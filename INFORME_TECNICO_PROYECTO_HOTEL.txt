2.7 ARQUITECTURA DEL BACKEND

Estructura de directorios:

├── src/

│   ├── routes/           # Definición de endpoints
│   ├── middlewares/      # Middleware de autenticación
│   ├── lib/              # Clientes (Supabase, Prisma)
│   ├── services/         # Servicios reutilizables
│   └── index.js          # Punto de entrada del servidor

Patrón MVC adaptado:
- Modelos: Definidos en Prisma Schema
- Vistas: No aplica (API REST devuelve JSON)
- Controladores: Lógica en controllers/
- Rutas: Mapeo HTTP en routes/

3. GESTORES DE BASE DE DATOS Y ESQUEMAS IMPLEMENTADOS
================================================================================

3.1 SISTEMA DE GESTIÓN DE BASE DE DATOS
----------------------------------------

• PostgreSQL (Proveedor: Neon.tech)
  - Base de datos relacional SQL
  - Conexión vía DATABASE_URL en .env
  - Soporte para transacciones ACID
  - Escalabilidad horizontal y vertical


3.2 ESQUEMA DE BASE DE DATOS (Prisma Schema)
---------------------------------------------

3.2.1 ENUMERACIONES (ENUMs)
---------------------------
- EstadoHabitacion: Disponible | Ocupada | Mantenimiento
- EstadoReserva: Pendiente | Confirmada | CheckIn | CheckOut | Cancelada
- EstadoFactura: Emitida | Pagada | Anulada
- EstadoConsulta: Pendiente | Respondida
- TipoEventoHabitacion: Apertura | Cierre | Mantenimiento
- Genero: Femenino | Masculino | NoBinario | PrefieroNoDecir | Otro
- TipoBloqueo: Mantenimiento | FueraDeServicio | BloqueoOperativo
- EstadoEmail: NoLeido | Leido | Respondido | Archivado | Spam
- PrioridadEmail: Alta | Media | Baja
- CanalEmail: Email | Web | WhatsApp


3.2.2 MÓDULO DE USUARIOS Y AUTENTICACIÓN
-----------------------------------------

Usuario (usuarios)
  - id: String (UUID de Supabase Auth)
  - nombre, apellido, fechaNacimiento, genero
  - telefono, direccion, provincia
  - estado: Boolean (activo/inactivo)
  - rolId → Rol
  - Relaciones: reservas, consultas, eventos, emails

Rol (roles)
  - id: Int (autoincremental)
  - nombre: String (Cliente, Operador, Administrador)
  - descripcion


3.2.3 MÓDULO DE HABITACIONES (Refactorizado)
---------------------------------------------

Categoria (categorias)
  - id, nombre, descripcion
  - Ej: Estándar, Deluxe, Premium

Ocupacion (ocupaciones)
  - id, nombre, capacidad, descripcionCamas
  - Ej: Doble Queen (2 personas), Triple Twin (3 personas)

TipoHabitacion (tipos_habitacion)
  - id, nombre (marketing), descripcion
  - categoriaId → Categoria
  - ocupacionId → Ocupacion
  - tarifaBase, superficie, vista, politicas
  - Relaciones: habitaciones, imagenes, amenidades

Amenidad (amenidades)
  - id, nombre, descripcion, icono
  - Ej: Wi-Fi, TV Cable, Minibar, Aire Acondicionado

TipoHabitacionAmenidad (tipos_habitacion_amenidades)
  - Tabla de unión Many-to-Many
  - tipoHabitacionId + amenidadId

ImagenHabitacion (imagenes_habitacion)
  - id, tipoHabitacionId, url, descripcion

Habitacion (habitaciones)
  - id, numero, piso, estado
  - tipoHabitacionId → TipoHabitacion
  - Relaciones: reservas, eventos, bloqueos


3.2.4 MÓDULO DE RESERVAS Y FACTURACIÓN
---------------------------------------

Reserva (reservas)
  - id, clienteId → Usuario, administradorId → Usuario
  - fechaIngreso, fechaEgreso
  - adultos, ninios
  - estado: EstadoReserva
  - totalAlojamiento, totalServicios, totalFinal
  - contactoEmail, creadaEn
  - Relaciones: habitaciones, servicios, factura, movimientos

ReservaHabitacion (reservas_habitacion)
  - Tabla de unión con detalles
  - reservaId + habitacionId
  - precioUnitario, subtotal, observaciones

Servicio (servicios)
  - id, nombre, descripcion, precioBase, estado
  - Ej: Desayuno, Cena, Traslado, Lavandería

ReservaServicio (reservas_servicios)
  - reservaId + servicioId
  - cantidad, precioUnitario, subtotal, fecha

Factura (facturas)
  - id, reservaId (unique), numeroFactura
  - metodoPagoId → MetodoPago
  - fechaEmision, subtotal, impuestos, total
  - estado: EstadoFactura

MetodoPago (metodos_pago)
  - id, nombre (Efectivo, Tarjeta, Transferencia)

ReservaMovimiento (reservas_movimientos)
  - Auditoría de cambios de estado
  - estadoAnt → estadoNuevo, cambiadoEn, operadorId


3.2.5 MÓDULO DE BLOQUEOS Y MANTENIMIENTO
-----------------------------------------

HabitacionBloqueo (habitaciones_bloqueos)
  - habitacionId, desde, hasta
  - motivo, tipo: TipoBloqueo
  - creadoPorId → Usuario
  - Índices en (habitacionId, desde, hasta)

HabitacionEvento (habitaciones_eventos)
  - Auditoría de eventos
  - habitacionId, adminId, tipo, detalle, fecha


3.2.6 MÓDULO DE COMUNICACIÓN Y CONSULTAS
-----------------------------------------

Consulta (consultas)
  - id, nombre, email, asunto, mensaje
  - estado: EstadoConsulta
  - creadaEn, respondidaEn, respuesta
  - operadorId → Usuario
  - emailVinculado → Email

Email (emails)
  - Sistema IMAP/SMTP de gestión de emails
  - messageId (unique), gmailId, threadId
  - deNombre, deEmail, paraNombres, paraEmails
  - asunto, cuerpoTexto, cuerpoHtml
  - canal: CanalEmail, prioridad, estado
  - fechaRecibido, fechaSincronizado, fechaLeido
  - operadorId → Usuario, consultaId → Consulta
  - Relaciones: adjuntos, respuestas

EmailAdjunto (emails_adjuntos)
  - emailId, nombreArchivo, mimeType, tamano
  - rutaLocal | urlS3 | dataBase64

EmailRespuesta (emails_respuestas)
  - emailId, operadorId
  - asunto, cuerpoTexto, cuerpoHtml
  - messageIdRespuesta, estadoEnvio, fechaEnviado


3.3 RELACIONES PRINCIPALES
---------------------------

- Usuario → Reservas (1:N): Un usuario puede tener múltiples reservas
- Reserva → ReservaHabitacion → Habitacion (N:M): Una reserva puede incluir varias habitaciones
- Reserva → ReservaServicio → Servicio (N:M): Una reserva puede tener servicios extra
- TipoHabitacion → Amenidad (N:M): Un tipo tiene varias amenidades
- Email → EmailRespuesta (1:N): Un email puede tener múltiples respuestas
- Habitacion → HabitacionBloqueo (1:N): Una habitación puede tener múltiples bloqueos


3.4 ÍNDICES Y OPTIMIZACIÓN
---------------------------

Índices creados en Prisma Schema:
- @@index([habitacionId, desde]) en HabitacionBloqueo
- @@index([deEmail]) en Email
- @@index([threadId]) en Email
- @@index([estado, prioridad]) en Email
- @@unique([categoriaId, ocupacionId, nombre]) en TipoHabitacion


3.5 MIGRACIONES Y SEEDS
------------------------

- Migraciones: Generadas automáticamente por Prisma
- Seed: prisma/seed.js para datos iniciales (roles, categorías, ocupaciones)
- Comando: npm run prisma migrate dev

4.1 API REST PROPIA (Backend)
------------------------------

Propósito: Comunicación entre frontend y backend del sistema hotelero

Arquitectura RESTful:
- Base URL: http://localhost:3000/api (desarrollo)
- Formato: JSON (application/json)
- Métodos HTTP: GET, POST, PATCH, DELETE
- Autenticación: JWT Bearer Token (Supabase Auth)


4.1.1 ENDPOINTS PRINCIPALES
----------------------------

** AUTENTICACIÓN **
POST   /api/auth/register      - Registro de usuarios
POST   /api/auth/login         - Inicio de sesión
GET    /api/auth/me            - Obtener usuario actual

** USUARIOS **
GET    /api/users              - Listar usuarios (admin)
GET    /api/users/:id          - Obtener usuario por ID
PATCH  /api/users/:id          - Actualizar usuario

** HABITACIONES **
GET    /api/habitaciones       - Listar habitaciones (paginado, filtros)
GET    /api/habitaciones/:id   - Obtener habitación específica
POST   /api/habitaciones       - Crear habitación (admin)
PATCH  /api/habitaciones/:id   - Actualizar habitación

** TIPOS DE HABITACIÓN **
GET    /api/tipos-habitacion   - Listar tipos con amenidades e imágenes
GET    /api/tipos-habitacion/:id - Obtener tipo específico
POST   /api/tipos-habitacion   - Crear tipo (admin)

** CATEGORÍAS Y OCUPACIONES **
GET    /api/categorias         - Listar categorías
GET    /api/ocupaciones        - Listar ocupaciones

** RESERVAS - FLUJO CLIENTE **
GET    /api/disponibilidad     - Consultar disponibilidad por fechas
POST   /api/pre-reservas       - Crear pre-reserva temporal
POST   /api/reservas           - Confirmar reserva con pago

** RESERVAS - GESTIÓN OPERADOR **
GET    /api/reservas           - Listar reservas (filtros, estados)
PATCH  /api/reservas/:id       - Actualizar estado de reserva
GET    /api/reservas/:id       - Obtener detalles de reserva

** PAGOS (STRIPE) **
POST   /api/pagos/create-checkout-session - Crear sesión de pago
POST   /api/pagos/webhook     - Webhook de Stripe (verificación)

** FACTURAS **
GET    /api/facturas/:id/pdf  - Generar factura en PDF

** EMAILS **
GET    /api/emails            - Listar emails (IMAP)
POST   /api/emails/:id/reply  - Responder email
PATCH  /api/emails/:id        - Actualizar estado (leído, archivado)


4.1.2 MODO DE INTEGRACIÓN (API PROPIA)
---------------------------------------

Frontend → Backend:
1. Cliente Axios configurado en frontend/src/services/
2. Token JWT almacenado en Supabase Session
3. Interceptores para agregar Authorization header
4. Manejo centralizado de errores (try-catch, toasts)

Ejemplo:
```javascript
// frontend/src/services/habitaciones.api.js
const response = await axios.get(`${API_BASE_URL}/habitaciones`, {
  params: { page: 1, pageSize: 10 }
});
```

Backend:
1. Middleware de autenticación valida JWT
2. Controladores procesan lógica de negocio
3. Prisma Client ejecuta queries
4. Respuesta JSON estandarizada


4.2 API SUPABASE (Authentication & Storage)
--------------------------------------------

Propósito: Autenticación de usuarios y almacenamiento de archivos

Servicios utilizados:
- Supabase Auth: Registro, login, gestión de sesiones
- Supabase Storage: Almacenamiento de imágenes de habitaciones

Integración Frontend:
```javascript
import { supabase } from '@/lib/supabase';
const { data, error } = await supabase.auth.signInWithPassword({ email, password });
```

Integración Backend:
```javascript
const { supabasePublic, supabaseAdmin } = require('./lib/supabase');
const { data: { user } } = await supabasePublic.auth.getUser(token);
```

Modo de integración:
- SDK oficial @supabase/supabase-js
- Cliente público (frontend) con anon key
- Cliente admin (backend) con service role key
- Tokens JWT validados en middleware


4.3 API STRIPE (Pagos Online)
------------------------------

Propósito: Procesamiento de pagos de reservas

Servicios utilizados:
- Checkout Sessions: Flujo de pago hosted
- Webhooks: Confirmación de pagos exitosos

Modo de integración:
1. Frontend solicita sesión de pago al backend
2. Backend crea Checkout Session con Stripe API
3. Usuario redirigido a Stripe Checkout
4. Stripe envía webhook al backend tras pago exitoso
5. Backend valida firma y actualiza estado de reserva

Endpoints:
- POST /api/pagos/create-checkout-session
- POST /api/pagos/webhook (raw body para verificación)

Formato: JSON
Autenticación: Secret Key en backend, Webhook Secret para verificación


4.4 API EMAILJS (Emails desde Cliente)
---------------------------------------

Propósito: Envío de emails de contacto desde formulario web

Modo de integración:
- SDK @emailjs/browser en frontend
- Configuración con Service ID, Template ID, Public Key
- Envío directo desde navegador sin backend

Uso:
```javascript
import emailjs from '@emailjs/browser';
emailjs.send(serviceID, templateID, formData, publicKey);
```


4.5 API FIREBASE (Analytics & Hosting)
---------------------------------------

Propósito: 
- Hosting del frontend

4.6 API GMAIL (IMAP/SMTP)
--------------------------

Propósito: Lectura y envío de emails institucionales

Servicios utilizados:
- IMAP (IMAPFlow): Lectura de bandeja de entrada
- SMTP (Nodemailer): Envío de respuestas

Modo de integración Backend:
1. IMAPFlow conecta a Gmail vía IMAP
2. MailParser extrae contenido y adjuntos
3. Almacenamiento en tabla Email
4. Nodemailer envía respuestas vía SMTP
5. Vinculación con modelo EmailRespuesta

Autenticación: Contraseñas de aplicación de Gmail
